# Деплой на свой VPS — чтобы моды не пропадали при обновлении

## Почему они вообще пропадали

База данных (`data/modbuild.db`) и все загруженные файлы
(`public/uploads/*`) специально не лежат в git — это данные, которые
появляются во время работы сайта, а не код. Если деплоить через Docker
командой `docker build` при каждом обновлении — Docker собирает файловую
систему контейнера заново из того, что скопировано в `Dockerfile`, а раз
данных там нет (и не должно быть) — контейнер каждый раз стартовал с
пустого места. Сайт не терял данные сам по себе — их просто не было в
новом контейнере.

Ниже — два рабочих способа, которые эту проблему исключают.

## Способ 1: Docker (рекомендуется, есть `docker-compose.yml`)

```
git clone <ваш-репозиторий> alem-mod
cd alem-mod
cp .env.example .env
nano .env   # заполните секреты — см. ниже "Полный .env"
docker compose up -d --build
```

Обновление после `git pull`:
```
git pull
docker compose up -d --build
```

`docker-compose.yml` пробрасывает `./data` и `./public/uploads` с диска
VPS внутрь контейнера как volume — они лежат отдельно от контейнера и
переживают любую пересборку. Дальше можно обновлять код сколько угодно —
моды, пользователи и файлы останутся на месте.

## Способ 2: без Docker, напрямую через Node + pm2

Этот способ вообще не подвержен проблеме — раз нет пересборки образа,
`data/` и `public/uploads/` просто лежат на диске и `git pull` их не
трогает (они в `.gitignore`).

```
git clone <ваш-репозиторий> alem-mod
cd alem-mod
cp .env.example .env
nano .env
npm install
npm install -g pm2
pm2 start server.js --name mod-hub
pm2 save
pm2 startup    # выполните команду, которую покажет — автозапуск при перезагрузке VPS
```

Обновление:
```
cd alem-mod
git pull
npm install     # только если менялся package.json
pm2 restart mod-hub
```

**Главное правило для обоих способов: обновляйте код через `git pull` в
той же папке, никогда не через удаление папки и клон заново.** Пока
`data/` и `public/uploads/` не удаляются вручную — они переживут любое
количество обновлений.

## Резервные копии — на всякий случай, а не только на переезд

Даже при правильном деплое имеет смысл иногда сохранять бэкап (сломанный
диск VPS ничего не спрашивает). Два способа получить его на сайте:

- Кнопка «Скачать резервную копию» на вкладке Настройки в админке.
- Просто скопировать `data/modbuild.db` и папку `public/uploads/` куда-то ещё (например,
  через `scp`/`rsync` по крону).

Восстановление — тоже два способа, оба применяются **сразу**, без
перезапуска сервера:

- Кнопка «Восстановить из резервной копии» в админке (загрузить .zip).
- Просто закинуть .zip резервной копии в папку `data/restore-inbox/` (по
  SFTP, через файловый менеджер Termux — как удобно) — сайт сам заметит
  файл в течение ~15 секунд, применит его и переложит в
  `data/restore-inbox/processed/`. Если что-то пойдёт не так — файл
  переименуется в `<имя>.zip.error` и не будет пытаться примениться снова.
