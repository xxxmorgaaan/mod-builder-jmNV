# Alem Mod — сайт (конструктор + каталог модов Alem Colony)

Один сайт, два раздела: **конструктор** (`/builder/` — собираете мод формами,
без ручного JSON) и **каталог** (всё остальное — публикация, поиск, сборки,
жалобы, баг-трекер, админка). Один сервер на Node.js + Express, данные — в
SQLite (файл, никакой отдельной БД поднимать не нужно).

Игра на сайте всегда одна — **Alem Colony**, она уже засеяна в базу при первом
запуске.

```
mod-hub/
├── server.js              Express-приложение, мидлвары, healthcheck + самопинг
├── Dockerfile              опционально: сборка вместе с ClamAV (см. раздел 9)
├── start.sh                стартовый скрипт для Dockerfile (freshclam + clamd + node)
├── src/
│   ├── db.js               подключение к SQLite, накат схемы, посев игры и владельца
│   ├── schema.sql           таблицы
│   ├── helpers.js           слаги, коды управления, CSV, размер файла
│   ├── upload.js            multer: обложки/скриншоты/архивы, типы и лимиты
│   ├── scan.js              проверка архивов: эвристика + опциональный ClamAV
│   └── auth.js              guard-мидлвары для админки
├── routes/
│   ├── pages.js             главная, каталог, страница мода, публикация, лайки, комментарии
│   ├── bundles.js           сборки модов + «скачать всё»
│   ├── complaints.js        жалобы как переписка
│   ├── bugs.js              баг-трекер (выключен по умолчанию, см. раздел 3a)
│   └── admin.js             модерация, таблицы, жалобы, баги, админы, настройки
├── views/                   EJS-шаблоны (+ views/partials, views/admin)
├── public/
│   ├── css/style.css        тема «Alem Mod» — космос + циан/янтарь с логотипа игры
│   ├── js/main.js           мобильное меню, лайки, лайтбокс, чат жалоб, коды в localStorage
│   ├── img/                  логотип и фавиконки (сделаны из значка игры)
│   ├── builder/              конструктор модов «Кузница модов» — раздел сайта, /builder/
│   └── uploads/              обложки/скриншоты/архивы/баги (создаётся при загрузке)
└── data/                    modbuild.db (SQLite) — создаётся сама при первом запуске
```

## 1. Запуск локально

Нужен Node.js 18+.

```bash
cd mod-hub
npm install
cp .env.example .env   # и поправьте значения — особенно OWNER_PASSWORD и SESSION_SECRET
npm start
```

Открыть: **http://localhost:3000**

При первом запуске сервер сам:
- заводит игру Alem Colony в базе;
- создаёт владельца админки с логином/паролем из `.env` (`OWNER_LOGIN` / `OWNER_PASSWORD`).

Смените пароль сразу после первого входа — вкладка «Настройки» в админке.

## 2. Переменные окружения (`.env`)

| Переменная | Для чего |
|---|---|
| `PORT` | порт сервера (Railway подставит свой сам) |
| `SESSION_SECRET` | секрет для подписи cookie сессии — впишите длинную случайную строку |
| `OWNER_LOGIN`, `OWNER_PASSWORD` | логин/пароль владельца, создаётся один раз при пустой таблице `admins` |
| `SITE_AUTHOR_NAME`, `SITE_AUTHOR_TELEGRAM` | автор сайта в подвале — по умолчанию МОРГАН / @Xxmorgaan |
| `GAME_DEV_TELEGRAM` | Telegram-канал **разработчика игры** Alem Colony (не путать с автором сайта) |
| `MOD_BUILDER_URL` | ссылка на конструктор модов — кнопка «Собрать мод» на главной |
| `PUBLIC_URL` | публичный адрес сайта после деплоя — включает встроенный самопинг (см. ниже) |

## 3. Модерация — как договорились

Новый мод, новая версия мода и новая сборка получают статус `pending` и
**не показываются в общем каталоге**, пока админ или модератор не нажмёт
«Одобрить» на вкладке **Модерация**. Автор при этом видит свою публикацию
сразу — по ссылке со своим кодом управления (и без кода тоже видна форма
«ещё на проверке», а не 404).

Есть ещё `hidden` (уже одобренную запись временно сняли с витрины, не удаляя)
и `rejected` (отклонили с комментарием, который увидит автор).

**Ручная проверка файлов.** В очереди модерации у каждого мода и версии
есть кнопка **«🔍 Посмотреть файлы»** — открывает содержимое архива прямо в
браузере: список всех файлов, JSON открывается отформатированным текстом,
картинки — превью. Ничего распаковывать самому не нужно. То же самое можно
открыть у любого мода и после одобрения (вкладка «Моды» → «🔍 Файлы») —
полезно, если позже пришла жалоба.

Автоматическая проверка (структура + безопасность, раздел 9 ниже) уже
отработала к этому моменту — иначе запись вообще не попала бы в очередь.
В самой очереди виден только простой значок «✓ автопроверка пройдена»,
без технических подробностей — подробности ни к чему, если нужно
убедиться самому, для этого и есть «Посмотреть файлы».

**Автопубликация, если админ не успел посмотреть.** Через
`AUTO_APPROVE_MINUTES` минут (по умолчанию 2) после публикации запись,
которую никто не одобрил и не отклонил вручную, публикуется сама — она уже
прошла автопроверку, дальше это просто вопрос того, что никто физически не
может сидеть и ждать каждую публикацию. Поставьте `AUTO_APPROVE_MINUTES=0`
в `.env`, чтобы отключить это и оставить только ручную модерацию без
исключений.

## 3a. Баг-трекер — готов, но выключен

`/bugs` — публичная доска багов (без модерации, сразу видно всем, как
форум): заголовок, описание, до 5 скриншотов, голосование, комментарии.
Статус (открыт / в работе / решён / не будем чинить) меняется в админке —
вкладка «Баг-репорты».

По умолчанию выключен: `BUGS_ENABLED=false` в `.env` — при этом `/bugs`
отвечает 404, а ссылки на него скрыты из шапки и подвала сайта. Поставьте
`true`, когда решите его объявить — код и вёрстка уже готовы, ничего
досдавать не нужно.

## 4. Публикация по коду, а не по аккаунту

Ни у модов, ни у сборок, ни у жалоб нет логина — вместо этого при создании
выдаётся код вида `<id>.<секрет>`. Код хранится в базе **обратимо
зашифрованным** (AES-256-GCM, ключ — `ENCRYPTION_KEY` в `.env`), а не
одноразовым хэшем — специально для того, чтобы админ мог его посмотреть.

Код автоматически сохраняется в `localStorage` браузера автора (страница
«Управление по коду» показывает список того, что там сохранено), но
браузер можно почистить, сменить телефон и т.п. — на этот случай на
вкладках **«Моды»** и **«Сборки»** в админке у каждой записи в столбце
«Код управления» виден настоящий код (клик — скопировать). Если автор
потерял код и написал вам в личку в Telegram — просто найдите его мод в
таблице и пришлите код обратно.

**Важно:** `ENCRYPTION_KEY` нельзя терять и нельзя менять просто так —
все уже выданные коды шифруются именно этим ключом, и без него их не
расшифровать (в таблице тогда покажется «не удалось расшифровать»).
Сгенерировали один раз при первом деплое — и всё, дальше не трогайте.

## 5. Скрытый вход в админку

Никакой видимой кнопки нет. Пять быстрых кликов по подписи автора в подвале
сайта открывают `/admin.html`. Прямой адрес тоже работает — он не спрятан от
поисковиков специально, просто на него никто не ссылается с сайта.

**«Ввожу правильный пароль, а всё равно пишет неверный логин или пароль»** —
самый надёжный способ починить это раз и навсегда:

1. В переменных окружения на Railway задайте `RESET_TOKEN` — любая длинная
   случайная строка (просто придумайте, например `xk92mPz7qRw...`), сохраните.
2. Подождите, пока Railway передеплоит сервис с новой переменной.
3. Откройте `https://ваш-домен/admin/emergency-reset` — впишите тот же
   токен, новый логин и новый пароль. Страница меняет их **прямо в базе,
   в этот момент**, без перезапуска — здесь нечему разойтись с `.env`, как
   могло случиться с `OWNER_PASSWORD` (см. ниже, почему так бывает).
4. Войдите новыми логином/паролем на `/admin.html`.
5. Уберите `RESET_TOKEN` из переменных окружения — без него страница
   восстановления отвечает 404, как будто её и нет.

**Почему вообще так бывает:** владелец создаётся в базе один-единственный
раз, при самом первом запуске. Если потом поменять `OWNER_PASSWORD` в
`.env` (или в Variables на Railway) — уже существующая запись в базе сама
по себе не обновится: это осознанно, чтобы случайный редеплой не сбрасывал
пароль, который вы сменили вручную через «Настройки». Есть и более
короткий путь для этого конкретного случая — `SYNC_OWNER_PASSWORD=true`
(поставить, задеплоить, войти, вернуть `false`) — но если он почему-то не
сработал (например, непонятно, подхватилась ли новая переменная), способ
через `RESET_TOKEN` выше сработает всегда, потому что не зависит от того,
что и когда прочитал процесс при старте.

## 5a. Резервная копия и перенос на другой хостинг

Вкладка **«Настройки»** в админке (видна только владельцу) → **«Скачать
резервную копию (.zip)»** — один архив со всем, что нужно для переезда:
файл базы `data/modbuild.db` и все загруженные файлы (`public/uploads/`:
обложки, скриншоты, архивы модов, картинки багов). Чтобы перенести сайт на
другой хостинг — разверните там код как обычно (раздел 1), затем
распакуйте этот архив в корень проекта той же структурой папок (можно
поверх только что созданных `data/` и `public/uploads/` — они изначально
пустые) и запустите сервер. Все моды, коды управления, лайки, комментарии
и жалобы переедут как есть.

## 6. Деплой на Railway + чтобы сервис не «засыпал»

1. Создайте проект на [railway.app](https://railway.app), подключите репозиторий.
2. Railway сам определит Node.js, `npm install` и `npm start` можно не трогать —
   но если нужно, Build Command оставьте пустым, Start Command — `npm start`.
3. Во вкладке Variables пропишите все переменные из `.env.example`, включая
   `PUBLIC_URL` = выданный Railway домен (`https://ваш-проект.up.railway.app`).
4. Диск: SQLite-файл и загрузки лежат в `data/` и `public/uploads/` — на
   Railway это эфемерная файловая система по умолчанию, при передеплое всё
   сотрётся. Подключите **Railway Volume** и примонтируйте его на `/app/data`
   и `/app/public/uploads` (в настройках сервиса → Volumes), иначе моды и
   пользователи «слетят» при каждом обновлении кода.

**Чтобы сервис не отключался:**
- Сервер сам пингует себя на `/healthz` каждые 4 минуты, если задан
  `PUBLIC_URL` — это подстраховка на случай, если план всё же засыпает от
  бездействия.
- Надёжнее — независимый внешний пинг: заведите монитор на
  [UptimeRobot](https://uptimerobot.com) или [cron-job.org](https://cron-job.org)
  на `GET https://ваш-домен/healthz` раз в 5 минут. Он работает, даже если
  сам процесс уже уснул — самопинг изнутри в этом случае не поможет, а
  внешний запрос как раз и будит сервис.

## 7. Конструктор модов — теперь часть этого же сайта

Раньше это был отдельный проект (`mod-builder`), сейчас его статика просто
лежит в `public/builder/` и открывается по адресу **`/builder/`** — отдельный
сервер для него не нужен, Express и так раздаёт всё из `public/`. Логика
конструктора полностью в браузере (формы, JSZip для сборки архива) — сервер
только отдаёт файлы, как и для остального сайта.

Кнопка «Собрать мод» на главной и в шапке ведёт на `/builder/`; на вкладке
«Экспорт» внутри конструктора после скачивания архива появляется ссылка
«опубликовать его на сайте» → `/mods/new`. Если когда-нибудь захотите
вынести конструктор обратно на отдельный домен — поменяйте `MOD_BUILDER_URL`
в `.env` и просто не кладите папку `builder/` в `public/` при следующем
деплое.

## 8. Чего в этой версии нет (сознательно, чтобы не раздувать MVP)

- Полнотекстового поиска (сейчас `LIKE` по названию и краткому описанию) —
  для каталога с сотнями модов этого достаточно, для тысяч — стоит перейти
  на FTS5 (SQLite это умеет «из коробки», можно добавить отдельным патчем).
- Восстановления кода управления на почту — почты в системе нет вообще,
  осознанный выбор в пользу анонимности без регистрации.

## 9. Автоматическая проверка загружаемых файлов

Каждый загруженный архив мода — и при первой публикации, и при загрузке
новой версии — проходит три проверки подряд, до того как файл вообще
попадёт в базу и очередь модерации:

1. **Эвристика по содержимому `.zip` — включена всегда**, без настроек.
   Открывает список файлов внутри архива (не распаковывая) и блокирует
   загрузку, если находит: исполняемые или скриптовые файлы (`.exe`,
   `.bat`, `.ps1`, `.sh`, `.js`, `.dll`, `.apk` и т.п. — мод для Alem
   Colony это только `mod.json` и картинки, им там не место), попытки
   выйти за пределы архива (`../` в пути), подозрительно много файлов или
   zip-бомбу (несжатый размер аномально больше сжатого).
2. **Сравнение структуры с обычным модом — тоже включено всегда.**
   Проверяет, что в архиве вообще есть `mod.json` и что он читается как
   JSON — без него или при поломанном JSON загрузка блокируется сразу, это
   явно не мод. Поля `id`/`name` в `mod.json` не обязательны (встречаются
   рабочие моды без `id` — сама игра, похоже, обходится и без него) —
   их отсутствие только попадает в заметку модератору, не блокирует. Остальные `*.json`
   (`weapons.json`, `apparel.json`, `resources.json`, `recipes.json`,
   `buildings.json`, `techs.json`, `pawns.json`, `loc.json`) должны быть
   рабочим JSON — если какой-то из них битый, загрузка тоже блокируется.
   Незнакомые файлы или поля верхнего уровня не блокируют публикацию, но
   попадают в заметку для модератора — мало ли, опечатка в имени файла.
3. **ClamAV — опционально, по умолчанию выключен.** Приложенный
   `Dockerfile` собирает сайт с инструментами для сборки `better-sqlite3`
   (нативный модуль — без `python3`/`make`/`g++` он не соберётся на Railway)
   и запускает `npm start` напрямую, без ClamAV — так проще и быстрее
   деплоится. Автоматической защиты от неизвестных вирусов при этом нет,
   только эвристика + сравнение структуры (пункты 1–2 выше), это честно
   помечается в `scan_note` каждой версии, чтобы модератор знал и мог сам
   посмотреть файл перед одобрением.

   Если хотите ClamAV — правьте `Dockerfile` руками:
   1. Добавьте в `RUN apt-get install`: `clamav clamav-daemon clamav-freshclam`.
   2. Поменяйте `ENV CLAMAV_ENABLED=false` на `true`.
   3. Поменяйте `CMD ["npm", "start"]` на `CMD ["./start.sh"]` (он в
      репозитории — обновляет базы сигнатур и поднимает `clamd` в фоне
      перед стартом сайта).

   Учтите: `freshclam` (обновление баз) при старте контейнера тянет базы из
   интернета — это заметно увеличивает время сборки/старта по сравнению с
   обычным деплоем.
Заблокированный проверкой файл **удаляется с диска сразу** и вообще не
доходит ни до базы, ни до очереди модерации — автор получает ошибку с
кратким объяснением, что именно не понравилось проверке.
